## 一、研究背景与目标

### 1.1 现状与痛点

我们当前的权限体系基于 **SQLite + Python** 自研，实现了 **9 种权限机制并存** 的复杂体系：

| 机制编号 | 名称 | 实现位置 | 主要问题 |
|---------|------|---------|---------|
| 1 | 功能权限 | DB 表 + Python 装饰器 | 与其他机制正交性差 |
| 2 | 维度范围白名单 | role_dimension_scope | 本质是条件表达式，但用 9 机制表达 |
| 3 | 可见性 | visibility_config | 与维度范围重叠 |
| 4 | Owner 例外 | owner_exception | 与 Owner 自动授权混淆 |
| 5 | 实例权限 | instance_permission | 颗粒度过细 |
| 6 | 条件规则 | condition_rule | 表达式引擎能力有限 |
| 7 | M11 YAML RLS | Row Level Security | 仅在 SQL 层，不在业务层 |
| 8 | 字段脱敏 | field_masking | 与权限决策割裂 |
| 9 | Owner 自动授权 | owner_auto_grant | 与 Owner 例外重复 |

**核心痛点**：
- **9 机制并存**导致权限决策路径复杂，难以追踪
- **缺乏统一抽象**，每新增一种场景就增加一种机制
- **性能问题**：每次权限检查需查 9 张表
- **维护成本**：权限代码遍布 20+ 模块
- **测试覆盖**：难以构造全面的回归测试

### 1.2 研究目标

本研究旨在：
1. **深入理解** 5 大主流开源权限引擎的架构设计
2. **横向对比** 各引擎的能力边界与适用场景
3. **评估借鉴** 哪些设计模式可以融入我们的体系
4. **决策参考** 是否值得替换或部分替换自研实现
5. **集成成本** 评估与现有 SQLite + Python 体系的集成难度

### 1.3 研究方法

- **WebSearch 搜索**：每个引擎搜索 2-3 次，共 14 次搜索
- **官方文档**：阅读 GitHub README、官方规范文档
- **基准测试数据**：从公开论文、博客获取性能数据
- **代码示例**：通过实际配置示例理解引擎语法
- **横向对比**：基于 7 个维度进行系统化对比

### 1.4 研究范围

本研究覆盖的 5 大开源权限引擎：

| 引擎 | 起源 | 核心模型 | 主要语言 | GitHub Stars (2026) |
|------|------|---------|---------|---------------------|
| **Casbin** | 2017 中国开源 | PERM (Policy/Effect/Request/Matcher) | Go (主) + 30+ SDK | 17k+ |
| **OPA** | 2016 Styra | Rego (Datalog based) | Go | 9.5k+ |
| **Ory Keto** | 2019 Ory | Google Zanzibar ReBAC | Go | 4.8k+ |
| **SpiceDB** | 2021 AuthZed | Google Zanzibar + Schema DSL | Go | 5.2k+ |
| **Cerbos** | 2021 Cerbos Labs | YAML 声明式 + CEL | Go | 3.5k+ |

## 三、根因分析（5-Why）

### Why 1: 为什么 staging 服务挂了？
- 进程被 stop --all 杀掉，没人重启

### Why 2: 为什么没人重启？
- staging 上**没有守护进程**

### Why 3: 为什么没有守护进程？
- 之前 P1-10 基础设施优化只做了 `staging_services.sh`（手动 start/stop）和 `log_service` 的 systemd unit
- **18081 / 13011 / 19200 三个服务没有 systemd unit 也没有应用层 watchdog**

### Why 4: 为什么之前没发现？
- staging 是低频使用环境（仅 PM 偶尔验证）
- 服务挂了没人立刻发现，直到用户访问
- 没有 health check → 没有告警 → 没有 on-call

### Why 5: 根本原因（系统性）
- **基础设施不完整**：4 个服务只覆盖了 1 个的守护
- **缺乏端到端监控**：健康检查只查 2 个 endpoint（漏 50%）
- **文档与现实脱节**：STAGING_GUIDE.md §0 错误声明 18081/13011 "dead"，掩盖了真实情况

## 四、修复方案（已实施）

### 4.1 应用层 watchdog（主方案）

**新增** [tools/staging_watchdog.sh](../../excel-to-diagram/tools/staging_watchdog.sh)，部署到 `/opt/app/staging/bin/staging_watchdog.sh`。

| 能力 | 描述 |
|---|---|
| HTTP 探测 | 每 30s 检查 4 个端口 (18081/13011/19101/19200) |
| 自动重启 | DOWN 时调 `staging_services.sh restart <name>`（依赖图正确） |
| 防雪崩 | 1h 内重启 ≥5 次 → ABORT，停止自动重启 |
| 状态查询 | `staging_watchdog.sh status` 一键看 4 服务 + 1h 重启次数 |

**部署**：
```bash
nohup bash /opt/app/staging/bin/staging_watchdog.sh --watch --interval 30 \
    >> /opt/app/staging/logs/staging_watchdog.log 2>&1 &
disown
# 当前 PID: 29059 (验证: bash staging_watchdog.sh status)
```

### 4.2 systemd unit（备选升级）

**新增** 4 个 .service 模板（[tools/staging-*.service](../../excel-to-diagram/tools/)）：
- staging-core.service
- staging-backend.service
- staging-spa.service
- staging-watchdog.service

**启用方法**（需 staging 服务器开放 systemd）：
```bash
cp tools/staging-*.service /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now staging-core staging-backend staging-spa staging-watchdog
```

### 4.3 健康检查升级

**升级** [tools/staging_health_check.sh](../../excel-to-diagram/tools/staging_health_check.sh) 从 2 endpoint 扩到 4 endpoint + watchdog 状态检查。

## 七、教训总结

### L1: 服务挂了必须 5 分钟内自动重启

任何 staging 服务 DOWN 后**不允许**状态保持超过 5 分钟不修复。watchdog 30s 检测 + restart 5s 启动 = 35s 恢复。

### L2: restart 必须拉上游依赖

`restart <name>` 只重启单服务，**不会拉上游依赖**。下次改 backend / DB schema 必须用 `restart-deps`。

### L3: 文档必须与现实同步

STAGING_GUIDE.md §0 错误声明 18081/13011 "dead"，导致问题被掩盖。**每月**巡检一次文档与实际部署的同步性。

### L4: 健康检查必须全覆盖

2 个 endpoint 不足以反映 4 服务健康。健康检查脚本必须覆盖全部服务。

### L5: 进程守护 = 多层防护

应用层 watchdog + systemd unit + 监控告警，**缺一不可**。任何单一机制失效都能让服务沉默地死掉。
